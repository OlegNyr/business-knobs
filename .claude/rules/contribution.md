# Правила разработки

**Стек:** Java 21 · Spring Boot 4 (BOM) · Jackson 3 · Lombok · OpenFeature · Micrometer
**Форма:** библиотека из модулей `api` → `impl` → `spring-boot` и плагин `business-knobs-maven-plugin`; пример `business-knobs-example` — отдельный проект
**Методология:** SOLID · TDD

Библиотеку подключают чужие сервисы, поэтому всё, что видно снаружи, — пакеты, имена
свойств `knobs.*`, метрик `knobs.parameters.*`, формат файла стенда, — меняется только
осознанно, с записью в ADR (`doc/adr/`) и в документах `doc/`.

---

## 1. Технологический стек

### 1.1. Java 21

- **Records** — для неизменяемых структур данных внутри библиотеки.
- **Sealed classes/interfaces** — для закрытой иерархии типов.
- **Pattern matching** (`switch`, `instanceof`) — вместо цепочек `if-else` и ручных кастов.
- **Text blocks** (`"""`) — для многострочных JSON и YAML в тестах.
- **`var`** — только когда тип очевиден из правой части. Не использовать, если ухудшает читаемость.
- Запрещено использование deprecated API и `sun.*` / `com.sun.*` пакетов.

### 1.2. Spring Boot 4

Spring нужен только модулю `business-knobs-spring-boot`; в `api`, `impl` и `generator` его нет
(границу держат зависимости Maven и тест-скан в `KnobsTest`).

- Бины — только через конструктор. Никаких `@Autowired` на полях или сеттерах.
- Настройки библиотеки — `@ConfigurationProperties` с префиксом `knobs` (`ParameterSettingsProperties`),
  с Javadoc на каждом поле: из него собираются метаданные для IDE.
- Автоконфигурация регистрируется через
  `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, а не через
  `@Import`: так её отфильтровывают slice-тесты сервиса.
- Необязательные функции (актуатор, метрики, ByteBuddy, SnakeYAML) — `optional`-зависимости и
  условия `@ConditionalOnClass`: сервис без них поднимается.

**Отличия Boot 4 от Boot 3, на которых легко споткнуться:**

- Пакеты тестовых slice-аннотаций: `org.springframework.boot.<модуль>.test.autoconfigure.*`
  (имя модуля ДО `test`), например `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`.
  Проверять пакеты по живому импорту, а не по памяти о Boot 3.
- `@MockBean` / `@SpyBean` удалены: `@MockitoBean` / `@MockitoSpyBean` из
  `org.springframework.test.context.bean.override.mockito`.
- Jackson: `Jackson2ObjectMapperBuilderCustomizer` → `JsonMapperBuilderCustomizer`;
  `@JsonComponent` → `@JacksonComponent`; свойства `spring.jackson.*` → `spring.jackson.json.*`.
- Переехавшие пакеты автоконфигураций: `org.springframework.boot.<модуль>.autoconfigure`.

### 1.3. Jackson 3

- **Пакеты**: `tools.jackson.*` вместо `com.fasterxml.jackson.*` — **кроме аннотаций**.
- **Исключение — `jackson-annotations`**: модуль аннотаций не переезжал, импорты остаются
  `com.fasterxml.jackson.annotation.*` (`@JsonProperty`, `@JsonCreator`, `@JsonValue` и др.).
- **Аннотации из `jackson-databind`** переехали: `@JsonSerialize`, `@JsonDeserialize`,
  `@JsonPOJOBuilder` → `tools.jackson.databind.annotation.*`.
- Библиотека не полагается на `ObjectMapper` приложения: модели связаны с Jackson явными
  аннотациями и читаются стандартным `JsonMapper.builder().build()`.
- `java.time.*` в Jackson 3 поддержан без модулей; `JavaTimeModule` регистрировать не нужно.
- Неизвестные поля файла стенда и записи топика пропускаются: это правило совместимости контракта.

### 1.4. Lombok

Разрешённые аннотации:

- `@Getter`, `@RequiredArgsConstructor`, `@Slf4j`.
- `@Value` + `@Builder` — стандартная пара для неизменяемых моделей; `@Singular` — для коллекций.
- `@SuperBuilder` + `@NonFinal` — если модель участвует в наследовании;
  `@EqualsAndHashCode(callSuper = true)` указывать явно.

Запрещено:

- `@Data` — скрывает поведение и генерирует небезопасные `equals/hashCode`.
- `@AllArgsConstructor` на публичных классах — делает API хрупким.
- `@SneakyThrows` — глотает контракт исключений.
- `@Setter` на уровне класса — нарушает инкапсуляцию.

Lombok в библиотеке — `optional`: в рантайм сервиса он не попадает.

## 2. Архитектура

### 2.1. Модули и границы

```
business-knobs-api          ← то, что видит код сервиса, и SPI; без Spring и без исполнения
        ↑
business-knobs-impl         ← всё исполнение без Spring: файл стенда, снимок, выбор значения
        ↑
business-knobs-spring-boot

business-knobs-maven-plugin ← плагин Maven; от модулей библиотеки не зависит — общий у них
                              только формат файла стенда (контракт)

business-knobs-example      ← НЕ модуль реактора: отдельный проект-потребитель, подключает impl и
                              плагин по координатам; собирается после ./mvnw install
```

- Зависимости строго однонаправленные. `api` импортирует только стандартную библиотеку, Jackson,
  Lombok, OpenFeature, context-propagation и себя — это держит `ApiBoundaryTest`.
- В `impl` нет Spring — это держит скан в `KnobsTest`. Всё поведение реализуется в `impl`;
  Spring-модуль только собирает классы `impl` и выставляет их Spring.
- Брокер, база реплики и HTTP-клиенты в библиотеку не входят: сервис реализует SPI
  (`ParameterReplica`) и зовёт применитель (`ParameterRecordApplier`).
- Новая публичная сущность — сначала в `api`, если её видит код сервиса; иначе — в `impl`.

### 2.2. Видимость

- Классы по умолчанию **package-private**. `public` — только то, что нужно снаружи пакета.
- Публичный класс `impl` — тоже API для тех, кто собирает библиотеку без Spring: менять его
  сигнатуры так же осторожно, как сигнатуры `api`.

## 3. SOLID

- **S — Single Responsibility.** Один класс — одна причина для изменения.
- **O — Open/Closed.** Для расширения поведения — новая реализация интерфейса или sealed-иерархия,
  а не правки существующего класса.
- **L — Liskov Substitution.** Наследник не усиливает предусловия и не ослабляет постусловия.
- **I — Interface Segregation.** Много узких интерфейсов лучше одного «толстого».
- **D — Dependency Inversion.** Исполнение зависит от портов (`ParameterReplica`,
  `ParameterObserver`), а не от конкретных хранилищ и регистров метрик.

## 4. TDD

### 4.1. Цикл Red → Green → Refactor

1. **Red** — написать падающий тест, описывающий новое поведение.
2. **Green** — написать минимальный код, чтобы тест прошёл. Не больше.
3. **Refactor** — улучшить структуру, не меняя поведения. Все тесты должны остаться зелёными.

Никакого продакшн-кода без предшествующего падающего теста.

### 4.2. Виды тестов

- **Unit (большинство)** — JUnit 5 + AssertJ, без Spring. Модели, выбор значения, разбор
  файла и заплатки, прокси групп.
- **Сборка без Spring** — `Knobs.builder()` над тестовым файлом стенда (`KnobsTest`).
- **Контекст Spring Boot** — `SpringApplicationBuilder` с `@ImportAutoConfiguration(ParameterAutoConfiguration.class)`
  и окружением, заданным в тесте (`SystemEnvironmentPropertySource` с `KNOBS_DC`,
  `KNOBS_DIMENSIONS`): так проверяется постпроцессор окружения, который работает до контекста.
- **Генератор** — эталонные файлы стендов из примера исходного YAML; цель плагина — юнит-тестом
  над `MavenProject` (`GenerateMojoTest`).
- **Пример** — `ExampleApplicationTest` проходит сценарий примера; он же проверяет, что
  установленный плагин отработал на сборке потребителя (`./mvnw -f business-knobs-example/pom.xml verify`).

Для проверяемости по времени — инжектить `Clock`, никаких `Instant.now()` напрямую.

### 4.3. Требования к тестам

- Именование: `methodName_shouldDoSomething_whenCondition`; `@DisplayName` — по-русски, о поведении.
- Структура AAA: **Arrange, Act, Assert** — с пустыми строками между блоками.
- Один тест — одно утверждение о поведении.
- AssertJ вместо JUnit-ассертов.
- Тесты не зависят друг от друга и от порядка выполнения.
- Покрытие — не самоцель: каждый сценарий и каждая ветка логики покрыты осмысленным тестом.

## 5. Общие требования к коду

- **Именование.** Классы — существительные, методы — глаголы. Без сокращений, кроме общепринятых.
- **Null.** `Optional` для возвращаемых значений, которых может не быть.
- **Immutability по умолчанию.** Коллекции наружу — неизменяемые копии. Поля — `final`.
- **Исключения.** Не ловить `Exception` без крайней необходимости, никогда не ловить `Throwable`.
- **Комментарии.** Объясняют «почему», а не «что». Ссылки на внутренние трекеры и чужие
  проекты в коде не пишутся.
- **Статический анализ.** `./mvnw -P quality verify`: Checkstyle, PMD, SpotBugs + FindSecBugs.
  Любое нарушение валит сборку; подавление — точечное, с обоснованием и условием снятия.

### 5.1. Логирование: значения параметров не печатаются

SLF4J через `@Slf4j`. Уровни: `ERROR` — требует реакции, `WARN` — аномалия (отбракованная запись,
неразрешённая подстановка), `INFO` — значимое событие (слой параметров поднят), `TRACE` — шаги
выбора значения.

Значение параметра может быть чем угодно, в том числе персональными данными или секретом,
попавшим туда по ошибке, а формы у такого значения нет — маской его не поймать. Поэтому:

- **В лог идут ключи, имена переменных, значения измерений пути и коды причин — но не значения
  параметров.**
- **Не печатайте текст исключения — печатайте его класс.** Строгие парсеры цитируют значение в
  сообщении (`DateTimeParseException: Text '…' could not be parsed`). Причина передаётся как
  `e.getClass().getName()`, а не объектом: `log.warn("...", e)` печатает стектрейс с сообщениями
  всей цепочки.
- Там, где исключение заворачивается в своё, причина не передаётся конструктору, если её текст
  может цитировать значение; это помечается `@SuppressWarnings("PMD.PreserveStackTrace")` с
  комментарием.
- Тест на лог проверяет обе стороны: значения в выводе нет **и** строка пригодна для разбора
  (ключ, класс причины).

## 6. Definition of Done

1. Поведение покрыто тестами (TDD-цикл пройден).
2. `./mvnw -P quality verify` зелёный.
3. Javadoc публичного API обновлён; изменение внешнего контракта отражено в `doc/` и ADR.
4. Нет `TODO` / `FIXME` без привязанной задачи.
