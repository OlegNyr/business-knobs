= ADR-0002: Библиотека — модули API, исполнение без Spring, Spring-адаптер, плагин генератора
:revdate: 2026-10-17
:status: accepted

*Статус:* accepted (2026-10-17) ·
*Контекст кода:* `ApiBoundaryTest`, `KnobsTest`

== Контекст

Библиотекой пользуются сервисы на Spring Boot и без него, а генератор файлов стендов — инструмент
сборки без Spring. Если действующий снимок живёт внутри `Environment` Spring, без Spring
библиотеку не собрать, а код сервиса видит и то, что вызывает, и внутренности.

== Решение

*Модули с односторонней зависимостью `spring-boot → impl → api`; плагин генератора от модулей
библиотеки не зависит.*

. `business-knobs-api`, пакет `io.github.olegnyr.knobs` — то, что видит код сервиса: чтение
  `Parameters` (с `client()` OpenFeature), путь контекста `ContextPath` и `ParameterContext`,
  событие `ParametersChanged` и `ParameterListener`, группы `@Knob`; SPI: реплика
  `ParameterReplica`, запись `ParameterRecord`, применитель `ParameterRecordApplier`, кодек
  `ParameterJson`.
. `business-knobs-impl`, пакет `io.github.olegnyr.knobs.impl` — всё исполнение без Spring: файл
  стенда, выбор значения, снимок `ParameterStore`, применитель, загрузчик реплики, рассылка смены,
  аварийная правка с аудитом, OpenFeature-провайдер, метрики Micrometer (необязательные),
  сборщик `Knobs.builder()`.
. `business-knobs-spring-boot`, пакет `io.github.olegnyr.knobs.boot` — адаптер: постпроцессор
  ставит снимок в `Environment`, автоконфигурация собирает классы `impl`, смена уходит слушателям
  контекста, актуатор зовёт аварийную правку. Своего исполнения нет.
. `business-knobs-maven-plugin`, пакет `io.github.olegnyr.knobs.generator` — плагин Maven, цель
  `generate`: файлы стендов на сборке сервиса и каталог вывода в ресурсах проекта. Разбор YAML
  не попадает в рантайм сервиса; общий у плагина и библиотеки только формат файла стенда —
  контракт, а не код. `StandFileGenerator` годится и для сборки без Maven.
. `business-knobs-example` — пример сервиса без Spring, отдельный проект вне реактора: подключает
  библиотеку и плагин по координатам, как настоящий сервис. Плагин, который используется в том
  же реакторе, где собирается, IDE при импорте не находит — поэтому пример не модуль.
. Границы держат зависимости Maven и тест-сканы: `ApiBoundaryTest` (API импортирует только
  стандартную библиотеку, Jackson, Lombok, OpenFeature, context-propagation и себя) и
  `KnobsTest` (в `impl` нет Spring).

== Последствия

*Хорошее.*

* Сервис без Spring собирает библиотеку кодом, Spring-сервис — подключением адаптера; работают
  одни и те же классы.
* Открытое API — это модуль, а не договорённость.

*Плохое.*

* Несколько артефактов: Spring-сервису достаточно `business-knobs-spring-boot`, остальные
  приезжают транзитивно, но версии модулей обязаны совпадать.
* API несёт Jackson и OpenFeature: запись и `client()` иначе не выразить.

== Пересмотреть, если

* появится потребитель, которому OpenFeature в API мешает: тогда `client()` уезжает из
  `Parameters` в отдельный интерфейс модуля `impl`.
