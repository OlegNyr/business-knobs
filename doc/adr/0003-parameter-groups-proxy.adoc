= ADR-0003: Группа параметров — прокси над слоем параметров; умолчания только в knobs.yaml
:revdate: 2026-10-17
:status: accepted

*Статус:* accepted (2026-10-17) ·
*Инструкция:* `doc/guide/howto-parameter-groups.adoc` ·
*Контекст кода:* `Knob`, `KnobKey`, `ParameterGroups`, `ParameterReader`,
`ParametersReader`, `ClassGroups`, `BinderParameterReader`, `EnableKnobs`,
`ParameterLookup`, `ParameterPropertySource`

== Контекст

Код сервиса хочет читать параметры типизированными геттерами (`routing.hopLimit()`), и каждый
вызов должен отдавать *действующее* значение — по пути пода и пути обращения на потоке.

Spring ходит в `Environment` в трёх режимах, и живой из них один: `@Value`, плейсхолдеры и
`@ConditionalOnProperty` читаются один раз при разборе конфигурации; `@ConfigurationProperties`
связывается один раз при создании бина; только ручной `Binder.bind` / `getProperty` читает
источник на каждом вызове. Объекта свойств с живыми геттерами у Spring нет; пересвязывание
Spring Cloud (`@RefreshScope`) перечитывает по событию, а не отвечает по контексту вызова.

== Решение

. *Группа — интерфейс с `@Knob(prefix)`*, за которым стоит JDK-прокси, *либо
  нефинальный абстрактный класс*, чей подкласс строит ByteBuddy (необязательная зависимость:
  без неё класс отбивается при создании с подсказкой, интерфейсы работают всегда). Ключ метода —
  префикс и `@KnobKey` либо kebab-case имени; `Optional<T>` — «значения нет» отличимо;
  иной тип без значения — `ParameterMissingException`; несовместимый тип —
  `ParameterTypeMismatchException`; `default`-методы исполняются как объявлены. Объявление
  проверяется при создании прокси, а не при вызове.
. *Прокси один, читатели разные.* Без Spring читатель — `Parameters`; со Spring —
  `BinderParameterReader`: `Binder` даёт конвертацию типов, списки с generics и relaxed-имена.
. *Умолчания только в `knobs.yaml`.* `Binder` читателя строится над одним источником —
  слоем параметров, а не над `Environment`. Ключ каталога без значения для пути — пустой ответ,
  а не значение переменной окружения или `application.yaml`.
. *Выбор значения один на все входы* — `ParameterLookup`: путь пода, явный путь вызова, путь
  потока.
. *Регистрация — явным `@EnableKnobs(basePackageClasses)`* в автоконфигурации модуля
  сервиса; автоскан пакета приложения не делается.

. *Имена отделены от свойств Spring.* Аннотации — `@Knob`, `@KnobKey`, `@EnableKnobs`; исходный
  файл — `src/main/knobs/knobs.yaml`, файлы стендов — `knobs/knobs-<стенд>.json`. По имени сразу
  видно, что значение приходит из библиотеки параметров, а не из `application.yaml` или
  `@ConfigurationProperties`.

== Последствия

* В бизнес-коде нет чтения свойств: тип и ключ объявлены в одном интерфейсе, который мокается в
  тестах как любой другой.
* Структурные ключи (`@ConditionalOnProperty`, плейсхолдеры аннотаций) остаются ключами
  окружения: они читаются один раз на старте, и контекст им не поможет.
* Под без файла стенда на первом чтении ключа получает `ParameterMissingException` — запасного
  значения нет.

== Отвергнутые альтернативы

* Пересвязывание `@ConfigurationProperties` по `ParametersChanged` — нет контекста вызова,
  мутация бина.
* Перехват геттеров конкретного класса с полями — поля расходятся с действующим значением.
* Spring Cloud `@RefreshScope` — лишняя зависимость и другая задача.
