= Контекстные параметры: файл стенда и запись топика
:revdate: 2026-10-17
:revnumber: 1.0
:status: draft

NOTE: Контракт между сервисом, подключившим `business-knobs`, и админкой параметров: сервис
читает файл своего стенда и записи топика, админка загружает файл стенда и публикует записи.
Админка — внешняя система, библиотека её не содержит: подойдёт любая, которая соблюдает этот
контракт. Исходный YAML, из которого собирается файл стенда, контрактом не является — это
формат разработчика (`doc/guide/knobs-example.yaml`).

== Участники

[cols="1,3", options="header"]
|===
| Сторона | Роль

| Сборка сервиса
| Генерирует из исходного YAML по файлу на стенд (`dev`, `test`, `prod`)

| Джоба загрузки (админка)
| Получает файл своего стенда параметром командной строки, грузит его в админку

| Админка
| Единственный писатель топика записей (в примерах — `knobs.parameters.v1`; имя выбирает
  владелец админки)

| Сервис (библиотека `business-knobs-*`)
| Читает файл своего стенда при подъёме и каждую запись топика; ничего не пишет
|===

== Файл стенда

JSON в кодировке UTF-8. В сборке сервиса лежит по пути `knobs/knobs-<стенд>.json`
от корня classpath — по нему сервис находит файл своего стенда. Пример ниже — фрагмент:
измерения и параметры показаны не все.

[source,json]
----
{
  "service": "orders",
  "version": "1.8.0",
  "stand": "prod",
  "dimensions": [
    { "key": "dc", "kind": "STAND" },
    { "key": "segment", "kind": "CODE", "values": ["MASS", "PREMIUM", "PRIVATE", "VIP"] }
  ],
  "parameters": [
    {
      "key": "app.crm.read-timeout",
      "name": "Таймаут чтения CRM",
      "type": "DURATION",
      "min": "PT0.1S",
      "max": "PT1M",
      "value": "PT10S",
      "rules": [ { "when": { "dc": "dc2" }, "value": "PT15S" } ]
    },
    { "key": "app.routing.project-enabled", "deleted": true }
  ]
}
----

.Корень файла
[cols="1,1,4", options="header"]
|===
| Поле | Обяз. | Смысл

| `service`
| да
| Сервис, чья сборка породила файл: `spring.application.name`

| `version`
| да
| Версия сборки. По ней админка отличает файл старше загруженного

| `stand`
| да
| Стенд, для которого собран файл

| `dimensions`
| нет
| Объявления измерений: `key` и `kind` — `CODE` (значения в `values`), `STAND` (значения ведёт
  администратор), `REGISTRY` (значения из другого справочника админки). Порядок объявлений без
  `service` — порядок точности пути

| `parameters`
| нет
| Параметры стенда. Параметра, у которого для стенда нет ни значения, ни правил, в файле нет
|===

.Параметр
[cols="1,1,4", options="header"]
|===
| Поле | Обяз. | Смысл

| `key`
| да
| Ключ — имя свойства Spring через точки, с префиксом сервиса

| `name`
| да, кроме удалённого
| Название для экрана админки

| `description`
| нет
| Пояснение

| `type`
| да, кроме удалённого
| `BOOLEAN` · `STRING` · `INTEGER` (целое 64 бит) · `DOUBLE` · `DURATION` · `DATE`. Незнакомый
  тип — несовместимое изменение: файл с ним не читается

| `list`
| нет
| `true` — значение есть список значений типа `type`

| `allowed`
| нет
| Выбор из списка: допустимые значения. Проверяет ручной ввод: админка и аварийная заплатка на
  поде

| `min`, `max`
| нет
| Границы в записи своего типа. Проверяют ручной ввод: админка и аварийная заплатка на поде

| `pattern`, `format`
| нет
| Ограничения формата строки; `format` — `url`. Только ручной ввод в админке: сервис эти поля не
  читает

| `value`
| нет
| Значение параметра: действует, когда не подошло ни одно правило. Длительность и дата —
  строкой ISO-8601 (`PT10S`, `2026-11-01`). Может содержать подстановку `${ИМЯ}`: её разрешает
  читатель файла — джоба по файлу значений, сервис по переменным окружения

| `rules`
| нет
| Правила: `when` — путь как объект «измерение → значение», `value` — значение правила.
  Одно правило на путь, порядка нет. Правило без `value` не действует. В файле стенда
  `value` правила, как и `value` параметра, может содержать подстановку `${ИМЯ}`; правило, чья
  подстановка не разрешилась, не действует, а параметр, у которого не разрешилась подстановка
  в `value`, значения из файла не даёт

| `deleted`
| нет
| `true` — параметр удалён; остальные поля не передаются
|===

Значение, полученное подстановкой, приводится к типу параметра: строка `true` у `BOOLEAN`,
`42` у `INTEGER`. Не приводится — значения из этого источника нет.

== Путь правила и выбор значения

Какие измерения есть и в каком порядке они уточняют друг друга, задаёт сам файл стенда:
объявления `dimensions` без `service`, в порядке объявления (ADR-0004). Настройка сервиса
`knobs.dimensions` (`KNOBS_DIMENSIONS`) нужна, только если файл измерений не объявляет;
заданная и расходящаяся с файлом — отказ на старте. Без объявлений и без настройки измерение
одно — ЦОД пода `dc`. В примерах ниже порядок такой: *ЦОД (`dc`) → арендатор (`tenant`) →
сегмент клиента (`segment`) → канал (`channel`)*.

Измерения нет в `when` — подходит любое значение; звёздочки в `when` не бывает, значение `"*"`
сравнивается буквально и ничему не соответствует. Условие `service` бывает только у общего
параметра: оно обязано совпасть, но в точность пути не входит.

Сравниваются только объявленные измерения и `service`; правило с иным измерением (например, из
записи админки) в выборе не участвует. Объявления `dimensions` нужны и админке — откуда брать
значения при вводе правила (`kind`, `values`), и сервису — порядок точности.

Правило подходит, если каждая названная часть пути совпала с путём контекста. Измерение,
которого нет в контексте, и измерение вне порядка пути правило не пропускают. Из подошедших
побеждает самое точное:

. у кого последняя названная часть стоит дальше в порядке;
. при равенстве — у кого названо больше частей;
. при равенстве — правило с условием `service` сильнее правила для всех сервисов;
. при равенстве — у кого названные части стоят дальше: `{tenant, segment}` точнее
  `{dc, segment}`.

Так выбор не зависит от порядка правил в файле или записи. Не подошло ни одно — `value`.

Для ЦОД `dc2` и сегмента VIP порядок такой: `{dc: dc2, segment: VIP}`, `{segment: VIP}`,
`{dc: dc2}`, затем `value`.

== Запись топика

Компактный топик (в примерах — `knobs.parameters.v1`), один на все сервисы. Пишет только
админка. Читает его сервис своим потребителем и отдаёт записи библиотеке
(`ParameterRecordApplier#applyAll`): брокер и клиент библиотека не выбирает.

[cols="1,4", options="header"]
|===
| Часть записи | Содержимое

| Ключ записи
| Ключ параметра. Поле `key` в теле необязательно; если оно есть и расходится с ключом
  записи, действует ключ записи

| Тело
| Слепок параметра в JSON — те же поля, что у параметра в файле стенда, плюс `version`
|===

.Поля тела сверх полей параметра
[cols="1,1,4", options="header"]
|===
| Поле | Обяз. | Смысл

| `version`
| да
| Версия параметра — время правки в миллисекундах, но не меньше прежней плюс один. Растёт при
  любой правке значения, правила или удалении
|===

Значение в записи всегда буквальное: текст с `${` читатель отбраковывает. Удаление —
запись с `deleted: true` и новой версией, а не пустое тело: пустое тело компактный топик
стирает, и подписчик, читавший дольше срока хранения, удаление пропустил бы. Записи удаления
достаточно полей `deleted` и `version`; `type` и `list` в ней необязательны.

Запись, у которой `type` или `list` расходятся с файлом стенда сервиса, читатель
отбраковывает: для сервиса это «значения из админки нет», действует значение из файла. Смена
типа параметра на стороне админки поэтому на сервис не влияет — тип задаёт файл стенда, то
есть сборка сервиса. Отбракованная запись не отменяет и аварийную правку на поде: её снимает
только принятая запись или запись удаления с версией позже момента правки. Админка может
периодически переопубликовывать весь набор с прежними версиями — читатель такие записи
игнорирует, поэтому повтор безвреден.

== Совместимость

Незнакомые поля читатель пропускает; `null` у признаков `list` и `deleted` равен их
отсутствию. Несовместимое изменение — новое значение `type` или `kind`, новый тип записи либо
новый топик `knobs.parameters.v2`, а не смена смысла поля.
